#Spec-Driven Development (SDD) & Quality Assurance Guide

Target Audience: Biblion Core Engineers, QA Testers & Reviewers

Authors: Biblion Evangelist in cooperation with Biblion Spec/QA Engineer

#1. SDD Framework Overview

Biblion practices rigorous Spec-Driven Development (SDD). Specifications in biblion-specs/ are living technical contracts that govern system behavior before implementation begins.

All specifications are written in Gherkin-aligned Markdown with clear behavioral boundaries, pre-conditions, and post-conditions.

#2. Implemented vs. Proposed Scenarios

Every specification document under biblion-specs/ partitions behavior into two explicit sections:

  1. Implemented Scenarios:
  • Reflect code currently merged into main.
  • Covered by automated unit, integration, or end-to-end tests.
  • Must pass in CI before any release.
  1. Proposed Scenarios:
  • Describe requested enhancements, new API endpoints, or revised UI workflows.
  • Carry metadata tag: Status: [PROPOSED].

#Approval Gate

CRITICAL RULE: Engineers must not write code for proposed features until Dr. Doronin reviews and marks the scenario as Status: [APPROVED].

#3. Test Suites & Verification Workflows

#Backend Verification (biblion-api)

  • Framework: RSpec, RuboCop, Brakeman (security scanner).
  • Run test suite:

```bash

cd /Users/sdoronin/workspace/biblion/biblion-api

bundle exec rspec

```

  • Run security and style scans:

```bash

bundle exec brakeman -q

bundle exec rubocop

```

#Frontend Verification (biblion-app)

  • Framework: Angular CLI, Jasmine, Karma.
  • Run unit tests:

```bash

cd /Users/sdoronin/workspace/biblion/biblion-app

npm test -- --watch=false --browsers=ChromeHeadless

```

  • Production build audit:

```bash

npm run build

```

#4. Markdown Specification Linting

All .md spec files in biblion-specs/ must pass formatting rules defined in .markdownlint.json:

bash
npx markdownlint-cli "biblion-specs/**/*.md"
